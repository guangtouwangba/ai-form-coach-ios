# 静态基线：实现细则与个人开发测试办法

日期：2026-10-15。承接 `2026-10-15-Pose-Calibration.md`。这是实施规格，当前 App 尚未实现本文独立静态采集器、录像回放入口和调试面板。

## 静态基线到底是什么

用户在相机前摆好分腿准备姿势，系统记录“本次从哪里开始、人体在图中多大、起始躯干倾角多少、关键点本身有多抖”。不要求全身绷紧，也不要求把前膝锁死。

不从静态姿势推断应该蹲多深，不把起始姿势本身认证为专业正确。机位/分腿站姿是否适合分析，由前置质量检查处理；个人动作范围由后续动态采样处理。

## 最小实现

### 输入与输出

输入每帧：采集时间戳、方向校正后的画面宽高、关键点与置信度、人体目标标识/检测数量的语义。先修正当前横纵坐标尺度，再做任何角度与距离运算。

优先用事先确认的可见侧肩/髋与训练腿膝/踝；不要求正侧面远侧所有点都持续可见。不在同一窗口内悄悄从一侧切换到另一侧取平均。

输出建议包括：

```text
StaticBaseline
  sourceGeometry / orientation / mirrored
  modelVersion / jointSelection / trainingSide
  hipPosition0 / shoulderPosition0
  torsoScalePx / trunkAngle0 / kneeAngle0
  frontAnklePosition0 / optionalRearAnklePosition0
  landmarkNoise / angularNoise
  validCoverage / stableDuration
  createdAt / invalidationReason
```

`torsoScalePx` 是二维画面中的尺度参照，不是身体真实厘米长度。没有可靠可见的远侧脚信息时，不声称已验证后脚支撑。

### 算法步骤

1. 取景/目标/关键点可用性通过后才开始采样，语音提示“保持准备姿势，正常呼吸”。
2. 使用按时间维护的滑动窗口，初始可试 2 秒；不写死 60 帧。窗口必须有足够有效采样和时间覆盖，不能用几帧稀疏数据冒充稳定 2 秒。
3. 分别统计髋位置、脚位置、人体尺度、躯干角。每项取中位数作为候选参考；同时保留离散度和窗口前后漂移。
4. 分开判断“关键点跳动很大”和“人在缓慢移动”。仅看方差或相邻帧速度会漏掉慢漂移。
5. 有效且稳定才提交基线；真正移动时重新等待稳定窗口。短暂缺失排除坏帧，超过允许缺失时间才重开窗口。
6. 提交后冻结初始参考。训练中不能持续更新起始高度而把缓慢下蹲吸收成新起点。

可用的特征示例：

```text
L = median(肩到髋的等尺度距离)
C = 坐标中位数组成的髋中心
hipJitter = P95(每帧髋位置到 C 的距离) / L
slowDrift = distance(前段髋位置中位数, 后段髋位置中位数) / L
scaleSpread = (P90(躯干尺度) - P10(躯干尺度)) / L
angleSpread = IQR(躯干角)
```

中位数基线与抖动大小都要看；不能因为“噪声大”就无限放宽通过线，否则检测不稳也会被自动适应。取景完全静止但站姿不适用时，可以通过稳定性检查，但必须被前置站姿门槛挡住。

### 第一轮参数怎么定

2 秒窗口、0.65 关键点分数只能作为初始工程候选；Vision 与 MediaPipe 分数不能直接互换。首轮先录制静止与移动素材，查看特征分布，再选择参数并在另一批录像上验证。

建议从髋/脚位置稳定性、慢漂移、有效时间覆盖三个条件开始，避免首版塞入几十个阈值。若要搜索参数，可以对窗口长度、稳定性阈值、缺失容忍时间做小范围网格比较；不能在同一批录像上调完就宣布准确率。

例如（纯说明，不是实测）：躯干参考尺度 300px，起始髋 y=700px，静止时髋点抖动约 3px；后续髋下降 60px，相对下降量为 60/300=0.20。它表达相对本次起点的位移，不能直接得出动作合格。

## 一个人怎么测试

### 第一层：不用人出镜的算法测试

使用已知坐标与时间戳的人工轨迹，覆盖：

| 输入 | 预期行为 |
| --- | --- |
| 稳定坐标加少量可控噪声 | 基线接近已知中心与尺度，在稳定窗口后完成 |
| 人体持续平移/慢慢下蹲 | 不应在移动期间完成静态采集 |
| 单帧离群点 | 不把离群点记成基线，也不使中位数剧烈变化 |
| 关键点长时间缺失 | 不应完成采集，并能指出缺失项 |
| 720×1280 与等比放大画面 | 同样姿态的角度与相对位移保持一致 |
| 原始采集 15/30Hz、带时间戳的掉帧 | 按真实覆盖时间判断，不以相同帧数假设相同时间 |
| 左右镜像/旋转 | 几何映射正确，人体左右语义不被镜像错误改写 |
| 稳定完成后开始下降 | 初始参考保持冻结，不跟着动作漂移 |

现有 `FixtureFactory` 与两项校准测试只覆盖部分理想动作和低分数情况；人工关键点测试不能验证 Vision 是否找对了真实关节。

### 第二层：自己录一套固定素材，反复回放

设备只需现有 iPhone、稳定支架/放置点和 Mac。用系统相机录制即可，先不改变正式 App 的“不保存视频”行为。后续如加开发录制入口，必须显式开启、明确只存本地，避免默认录制。

先准备下列 8–10 段短片，左右训练腿都留样本：

| 素材 | 检查目的 |
| --- | --- |
| 摆好准备姿势，稳定保持后开始动作 | 正常完成，基线不受后续下蹲污染 |
| 先晃动，再保持稳定 | 只在后面的稳定阶段通过 |
| 持续小步移动或慢慢降低身体 | 不把慢移动当静止 |
| 遮挡训练腿膝/踝或脚出框 | 门槛拦截/具体失败原因 |
| 更换照明/背景 | 发现关键点不稳定场景 |
| 镜头调整后重新摆好 | 原基线失效，新机位重新采集 |
| 仅普通站立，身体很稳定 | 静止判定可通过，分腿准备姿势门槛不能放行 |
| 同姿势不同距离 | 相对特征尺度适配，不应因单纯放大图像改变角度 |

每段记录一份简单标注：什么时候开始稳定、哪些点被遮挡、是否移动手机、期望通过/失败。用电脑暂停几帧人工点肩/髋/膝/踝，可以定位明显检测偏移，但这只是二维可审计对照，不是三维运动学金标准。

回放链路必须共用实时输入后面的处理代码：

```text
视频文件 → 解码帧和原始时间戳 → 同一 PoseProvider
        → 同一坐标转换/质量门槛 → 同一静态基线采集器
```

不能回放一段已经生成的理想骨架就声称真实视觉通过。建议同时支持视频回放和 JSON 关键点回放：前者验证视觉链，后者快速定位算法回归。

保持视频方向与镜像元数据一致；跳转或重播时清空跟踪器和采集器；按原始采集时间判断窗口。回放可加速，但不能让处理速度改变“稳定两秒”的含义。

模型/系统版本固定时，比较行为与特征容差，不要求浮点输出逐位完全一致。若通过手机 IMU 判断机位移动，录像本身不能替代同步 IMU 日志；该项需要真实设备或同步记录的传感器输入。

MediaPipe 官方 iOS 示例支持视频与实时流，具备这类验证入口；本项目目前还没有该回放工具。[官方 iOS 示例与指南](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/ios)

### 第三层：回到真机验证完整体验

每天只需选少量代表场景复测，重点验证录像回放不能覆盖的部分：相机预览、采集时延、实际分辨率/方向、机位移动传感器、语音时机与长时间运行。

开发模式提供 5 秒准备倒计时与完成/失败语音，方便一个人走到机位前，不必边看手机边维持姿势。倒计时结束若还没站稳，继续等待稳定窗口，不能到点自动成功。

调试面板最低需要展示：

- 骨架与选用关节，关键点分数。
- 等尺度坐标、身体尺度、髋/脚位移曲线、稳定窗口进度。
- 当前未通过原因，而不是统一写“请保持全身入镜”。
- 完成时间、重试次数、失效原因、模型/算法版本。

## 最初的验收边界

对人工轨迹验证几何与状态逻辑，对自己录像验证可重复运行和失败原因，对真机验证采集/性能/交互。自己的样本能帮助完成开发闭环，但不能证明适用于其他体型、衣着、关节活动范围或环境。

把自己另一日拍摄的录像留作不参与调参的测试集；后续找其他参与者时按人划分数据。不要以同一人的相邻视频帧拆分训练/测试来证明泛化。

## 建议先交付的工具

1. `StaticBaselineCollector`：独立纯数据采集器，时间窗口、稳健统计和明确失败原因。
2. `PoseReplayRunner`：同一模型与处理链的视频/关键点回放入口。
3. 开发调试页：骨架、曲线、通过/失败解释与本地日志。

先让这些工具能回答“为什么通过/为什么失败”，再扩大动作纠错规则。
